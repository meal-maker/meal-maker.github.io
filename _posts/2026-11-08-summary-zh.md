### [GitHub 新架构 Rubicon 支持每秒 7200 次推送](https://github.blog/engineering/architecture-optimization/inside-githubs-new-git-storage-architecture/) ⭐️ 8.0/10

GitHub 宣布了代号 Rubicon 的新 Git 存储架构，主要面向大量 AI 智能体并发操作单个仓库的场景。内部测试显示，该架构可支持 5000 个智能体同时协作，每秒处理 7200 次推送，并保持较低读取延迟。技术上，Rubicon 将 Git 对象存入 Azure Blob Storage，引用状态由 Ref-CAS 管理，由虚拟副本处理读写，后台节点负责压缩数据包。目前 Rubicon 处于有限私有预览阶段，GitHub 计划逐步扩大推广范围。

telegram · zaihuapd · 11月7日 14:12

**「背景」** Git 仓库由对象和引用组成，每次向 GitHub 推送通常会产生新的 pack 文件。Azure Blob Storage 是微软的对象存储服务，适合存放代码等大量数据。本次改动将存储与计算解耦，用对象存储保存 Git 对象，并在高写入速率下进行压缩。

**「影响」** 对于需要大规模 AI 智能体并发写入同一仓库的团队，Rubicon 有望提供更高推送吞吐和更低延迟，但当前私有预览意味着普通用户和公开仓库短期内无法直接采用。

### [Claude Code 本地设置泄露密码至 1122 个 GitHub 公开文件](https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again) ⭐️ 7.0/10

Apiiro 的扫描发现，1122 个公开 GitHub 文件中包含来自 Claude Code 本地存储的“Don&\#x27;t Ask Again”命令批准中的密码，这些文件因开发者误提交本地设置而泄露。这并非 Claude Code 工具本身的直接漏洞，而是 AI 编码代理带来的凭据泄露风险。Claude Code 团队表示，.claude/settings.local.json 本应保留在本地，Claude 创建该文件时会自动加入 gitignore，但本次案例中的文件是手动创建并提交的。团队还表示正在研究如何防止此类泄露。

hackernews · shmulc · 11月7日 20:45 · [社区讨论](https://news.ycombinator.com/item?id=50407882)

**「背景」** Claude Code 是 Anthropic 的智能体编码工具（tool-1-2），其本地 .claude/settings.local.json 文件用于存储用户通过 “Don&\#x27;t Ask Again” 批准的终端命令。该文件设计为仅保存在本地，不应提交到版本控制；但若开发者手动创建或未正确配置 .gitignore，包含内嵌密码的已批准命令可能随代码公开。此次 Apiiro 扫描发现 1,122 个公开 GitHub 文件暴露了此类密码，表明这一问题已实际造成秘密泄露。

**「影响」** 提交了.claude/settings.local.json 且其中包含带密钥命令批准的开发者，其密码已公开暴露，需要立即轮换凭据并清理相关文件。

**「社区讨论」** 评论普遍认为该问题不是 Claude Code 的直接缺陷，而是用户手动提交本地设置导致；社区建议使用密码管理器 CLI 或隔离虚拟机来限制 AI 代理对凭据的访问。

### [Coldframe：模拟超市制冷控制器的开源蜜罐](https://github.com/hedgerow-dev/coldframe) ⭐️ 7.0/10

Coldframe 是一个单文件 Python 蜜罐，可以伪装成 Danfoss AK-SM 800A 和 Dixell XWEB 超市制冷控制器界面，仅使用标准库构建，并基于 eppser/danfoss-ak-sm-decoy 以及 Synacktiv、Claroty 和 Ironhackers 的公开研究。它通过 Shodan 记录匹配真实设备特征，包括头部顺序、页面标题、证书字段和 TLS 版本，其中 Dixell 伪装不发送 Server 头并将页面填充到恰好 8,202 字节。该蜜罐能识别 CVE-2025-41450、Danfoss“当日代码”登录绕过，并标记针对另外三个 Danfoss CVE 和 XWEB 漏洞的尝试，默认登录会打开带除霜按钮的假仪表盘以观察后续动作。两个实例上线一天后仅看到通用扫描器和 Shodan 爬虫（refrigerator.census.shodan.io）。

hackernews · hedgerow-dev · 11月7日 17:27 · [社区讨论](https://news.ycombinator.com/item?id=50406292)

**「背景」** Danfoss AK-SM 800A 和 Dixell XWEB 是用于超市制冷系统的联网控制器，近期工业制冷设备遭受攻击事件引发关注。蜜罐是一种故意暴露的仿真系统，用于引诱攻击者并记录其行为。Coldframe 通过模仿这些设备的真实网络特征，让 Shodan 将其识别为真实设备而非蜜罐。

**「影响」** 安全团队可以在不依赖专用硬件或额外 Python 包的情况下部署该蜜罐，识别针对 Danfoss AK-SM 800A 和 Dixell XWEB 的 CVE-2025-41450、登录绕过及其他攻击尝试。但目前公开实例尚未捕获到真实攻击流量，实际检测效果需要更多部署验证。

**「社区讨论」** 评论中有人质疑仅依赖 Shodan 数据复制设备特征可能学到其他蜜罐或被入侵设备的痕迹，建议直接获取真实设备进行探测；作者补充血库冰箱可能成为更敏感目标，并指出超市缺乏安全团队，补丁和默认安全需要由厂商或安装商负责。也有评论追问近期大规模冰箱故障是否确认为黑客攻击，还是可能由集中软件更新导致。

### [MaxxBench：DeepSWE 高分可信吗？](https://maxxbench.unlap.ai/research/why-maxxbench/) ⭐️ 7.0/10

MaxxBench 通过改变任务规格来压力测试 DeepSWE 的高分，发现结果显著不稳定，尤其在小模型上退化明显，引发对基准可靠性的担忧。例如，带“-flash”后缀的较小模型和 OpenAI Luna 在变化下崩溃最严重，而 GPT 5.6-Sol 比 GPT 5.6-Luna 更稳健；评论者指出 GLM-5.3 与 GLM-5.3-flash 是不同谱系，不应按同一规律预期。此外，评论还提到 DeepSWE 本身存在多个 bug，实验室的 RL 环境可能未准确反映基准任务，较小模型可能过度拟合简化环境。

hackernews · antiuniverse · 11月7日 17:19 · [社区讨论](https://news.ycombinator.com/item?id=50406222)

**「背景：MaxxBench 与 DeepSWE」** DeepSWE 是一个旨在缓解测试集污染、仓库覆盖窄、任务描述过细和验证器不可靠等问题的长程软件工程基准。MaxxBench 选取其中 89 个任务，仅小幅修改指令或起始代码（如要求小写文件名或 UTC 时间戳），改动中位数仅 17 行（3.5%），以检验模型是真正适应新需求还是依赖原基准中的记忆或猜测。这一方法用于压力测试 DeepSWE 分数在不同任务规格下的稳定性。

**「社区讨论」** 社区普遍认可这种通过改变任务规格检验基准泛化性的思路，但也有人指出具体参数选择会影响信息量。讨论焦点包括小模型崩溃最明显、DeepSWE 的 bug、RL 环境与基准任务不匹配，以及小模型可能对简化环境过拟合。
