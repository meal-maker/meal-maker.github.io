### [Rust 1.100 Stabilizes Never Type, Custom Allocators, and Cargo Cooldowns](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 8.0/10

Rust 1.100, released on November 12, 2026, stabilizes the long-awaited never type \(\`\!\`\) and custom allocators, alongside major Cargo improvements. The release introduces minimum publish age configurations, also known as dependency cooldowns \(RFC 3923\), which let the resolver ignore versions published more recently than a configured threshold unless they are already in Cargo.lock. Cargo now warns about unused dependencies by default, and \`cargo install\` uses the existing lockfile in \`.crate\` tarballs by default, making \`--locked\` a no-op. Commenters also highlighted additional stabilized APIs not mentioned in the blog post, including \`bool::toggle\(\)\`, \`Box::map\(\)\`, \`str::trim\_prefix\(\)\`, \`str::trim\_suffix\(\)\`, and \`Path::trim\_prefix\(\)\`.

hackernews · mbStavola · Nov 12, 18:39 · [Discussion](https://news.ycombinator.com/item?id=50472038)

**「Background」** The never type \(\`\!\`\) represents computations that never return and has been a long-awaited feature in Rust; custom allocators allow programs to replace the default global memory allocator for finer control over memory. Cargo previously lacked a built-in dependency cooldown mechanism, and the min-publish-age configuration now adds an optional waiting period before newly published versions are selected.

**「Impact」** Rust developers can now use the never type and custom allocators as stable language and standard library features, and Cargo users gain safer dependency resolution through cooldowns and unused dependency warnings.

**「Community Discussion」** Commenters welcomed the release as monumental, highlighting never type, custom allocators, dependency cooldowns, unused dependency warnings, and additional stabilized APIs like \`bool::toggle\(\)\` and \`Box::map\(\)\`. Some users expressed frustration with compile times and large temporary artifacts requiring frequent \`cargo clean\`.

### [UMAP 0.6: Faster Performance, New Initialization and Optimizers](https://www.reddit.com/r/MachineLearning/comments/1xudaah/umap_06_new_initialization_new_optimizers_and/) ⭐️ 8.0/10

UMAP 0.6 has been released with major performance and quality improvements for large-scale dimensionality reduction. The nearest neighbor search is roughly 4x faster using PyNNDescent, and a new recursive initialization scheme lays out a coarse graph structure that refines into a starting point closer to the final layout than spectral or PCA initialization. New optimizers use hard-negative mining and better handle high repulsion strengths, improving kNN recall and revealing finer cluster structure. On 3 million arXiv papers, UMAP 0.6 finishes in under 5 minutes, while a seeded UMAP 0.5 run takes 52 minutes single-threaded. The new initialization and optimizers are opt-in via compatibility\_layout=False and will become default in future versions.

reddit · r/MachineLearning · /u/lmcinnes · Nov 12, 13:51

**「Background on UMAP and the 0.6 transition」** UMAP \(Uniform Manifold Approximation and Projection\) is a widely used Python library for dimensionality reduction and visualization of high-dimensional data. Its 0.5 release used a single nearest-neighbor, initialization, and layout-optimization pipeline; version 0.6 is a transition release that keeps that 0.5.x behavior as the default while introducing an opt-in new pipeline. The new pipeline includes recursive initialization and Adam/momentum-based optimizers.

**「Impact」** Users working with million-scale datasets can expect substantially faster UMAP runs and better neighborhood fidelity when enabling compatibility\_layout=False, though output layouts will change from previous versions.

### [Turning a 22-year-old Postgres type-confusion primitive into RCE](https://mehmetince.net/part-3-6-how-i-ended-up-turning-a-22-year-old-postgresql-type-confusion-primitive-into-rce-cve-2026-6460/) ⭐️ 7.0/10

A detailed technical write-up describes how a 22-year-old PostgreSQL type confusion primitive can be exploited to achieve code execution after authenticated database access, assigned CVE-2026-6460. The exploit hinges on the internal Datum representation, which may be either a pointer or a non-pointer value with its type identifier stored separately, allowing type confusion to be leveraged into arbitrary code execution. The attack requires an authenticated database account, so while it is a serious security issue, it is more accurately characterized as privilege escalation than remote unauthenticated code execution. The article has generated substantive discussion about PostgreSQL internals and the severity classification.

hackernews · ozirus · Nov 12, 18:22 · [Discussion](https://news.ycombinator.com/item?id=50471761)

**「PostgreSQL type confusion and CVE-2026-6460」** PostgreSQL&\#x27;s internal Datum representation can hold either a pointer or an inline value, with a separate type identifier that must stay bound to the datum; a type confusion occurs when code treats the datum as the wrong type after an ALTER ... SET DATA TYPE operation. This flaw, present for about 22 years, was fixed in November 2026 as CVE-2026-6460, part of a release that addressed 52 CVEs and introduced composite attribute versioning.

**「Impact」** PostgreSQL administrators, especially those running multi-tenant database instances, should apply the latest security releases, which bundle CVE-2026-6460 among 52 fixes with several CVEs rated around CVSS 8.8, because this flaw enables an authenticated database user to escalate privileges and potentially execute code on the server.

**「Community Discussion」** Several commenters, including logophobia and jmuguy, argue that because the exploit requires authenticated database access, it should be considered privilege escalation rather than remote code execution, particularly relevant for multi-tenant database scenarios. Others praise the write-up for explaining the path to the zero-day and database internals, while amluto criticizes the internal Datum design with type IDs stored separately as risky, calling it beyond &\#x27;code smell&\#x27; and into &\#x27;code reek&\#x27;.

### [Open-Source Project Runs 16B LLMs on Devices with Under 1GB RAM](https://github.com/hyperionaidev/smolmaxxing/) ⭐️ 7.0/10

An open-source project called smolmaxxing is optimizing LLM inference for small and old devices, and its author reports running 16B-parameter models on an iPad Air 1st generation and a Xiaomi TV box, both with less than 1GB of usable memory. The effort includes open-sourced kernels and modified models published on Hugging Face under the hyperionaidev account. The project aims to enable reproduction and further optimization on resource-constrained hardware. The reported runs are early and have not been independently verified.

hackernews · mrashad74 · Nov 12, 15:23 · [Discussion](https://news.ycombinator.com/item?id=50468888)

**「Low-memory LLM inference」** Running large language models locally typically requires keeping the entire model in RAM, which makes models with billions of parameters impractical on devices with less than 1GB of usable memory. The smolmaxxing project addresses this by running 8B and 16B mixture-of-experts models on about 1GB of RAM, keeping only part of each model in memory and reading the rest from flash storage as needed.

**「Impact」** According to the project&\#x27;s reported results, owners of very low-memory devices like the 2013 iPad Air \(about 700 MB usable\) and Xiaomi TV Box S \(3rd Gen, about 1 GB usable\) can run 16B MoE models at 2.6–5.1 tokens/s using the open-source smolmaxxing patches and modified models. These early figures have not yet been independently verified.

**「Community Discussion」** Commenters are generally enthusiastic about optimizing small models for old hardware, with one noting that modern AI agents can already assist with such tasks and another reporting progress with a locally trained 6.5M-parameter model. Some practical experience suggests performance varies with model size and task specifics.
