### [OpenAI pipeline eliminates ~1,000 Linux kernel privilege escalation paths to root](https://openai.com/index/a-thousand-fewer-paths-to-root/) ⭐️ 8.0/10

OpenAI reported that its autonomous vulnerability research pipeline scanned the Linux kernel in October 2026 and dynamically reproduced 1,724 vulnerabilities, generating 948 working local privilege escalation exploits and 291 information leak proofs of concept. The effort cost $1,213,430 in API usage, averaging about $1,279 per successful local privilege escalation exploit \($359 per exploit development cost\), and identified at least 10 new exploitation techniques confirmed by third-party experts. These vulnerabilities allowed local unprivileged users to gain root, and their elimination represents a significant reduction in the kernel&\#x27;s attack surface. Based on historical Pwn2Own/TyphoonPWN bounty rates of $20,000 to $70,000 per exploit, the 948 issues would have a theoretical value of $18.9 million to $66.3 million.

hackernews · dangelosaurus · Nov 4, 23:33 · [Discussion](https://news.ycombinator.com/item?id=50372929)

**「Background」** Linux is a widely deployed open-source operating system kernel, and a local privilege escalation \(LPE\) vulnerability allows an attacker who already has a limited user account to gain root-level control. Because the kernel is millions of lines of C code, manual auditing cannot catch every bug, which has motivated automated vulnerability discovery and exploitation research. OpenAI describes an autonomous vulnerability discovery, exploitation, and patching pipeline using a cyber model, which in one run reproduced 1,724 vulnerabilities and produced 948 distinct LPE exploits for Linux at an API cost of about $1.2 million.

**「Impact」** Linux kernel users and administrators now have nearly a thousand fewer documented local privilege escalation paths to root, reducing the risk from local attackers, though the scan did not cover all possible kernel vulnerabilities.

**「Community Discussion」** Commenters expressed shock at the scale of 948 privilege escalation vulnerabilities, questioning how the internet remains functional and whether the kernel&\#x27;s complexity makes such flaws inevitable; some suggested immutable operating systems like Talos OS as a mitigation.

### [Anthropic Advances Provable Inference for LLM Outputs](https://www.anthropic.com/research/provable-inference) ⭐️ 8.0/10

Anthropic has shared progress on provable inference for large language models, describing a cryptographic method to verify that model outputs were generated by a specific set of weights. The approach uses a commitment of about 6.5 MB that remains valid for roughly 16 million requests before recommitment is needed, and each request produces a proof that can be checked in 17 seconds on 24 threads or 21 seconds on a single thread. The technique comes with a reported compute overhead of approximately 90–100x compared to normal inference. This work aims to address trust and safety concerns by allowing clients to confirm which model actually produced a response, though the overhead is significant and early-stage.

hackernews · ltononro · Nov 4, 17:17 · [Discussion](https://news.ycombinator.com/item?id=50368626)

**「Background」** Provable inference uses zero-knowledge Succinct Non-interactive Arguments of Knowledge \(zkSNARKs\) to produce a cryptographic proof that a specific model generated a specific output, allowing a verifier to check the claim without rerunning the model. Anthropic&\#x27;s FlashProve system applies this technique to large mixture-of-experts language models, as described in a technical report and companion blog post, and represents an early research prototype for verifying closed model providers.

**「Impact」** For closed-model API users, this could eventually let them cryptographically verify that responses came from the advertised model rather than a substitute or misconfigured server, but current 90–100x compute overhead and ~17-second proof checking limit practical use.

**「Community Discussion」** Commenters note prior work by MARS fellow neuwirth and VerInf with little attribution, and debate practicality: nemo1618 argues open-weight models can just be recomputed, while vessenes says closed providers could use cheaper probabilistic checks from multiple independent providers instead of the 90–100x ZK overhead. Others flag that the commitment covers ~16 million requests and point to potential use in detecting model substitution on routing services.

### [NKI Layer Megakernels Cut GLM-5.3-Flash Decode Latency on AWS Trainium2](https://www.reddit.com/r/MachineLearning/comments/1xo0yuq/p_nki_layer_megakernels_for_glm53flash_on_aws/) ⭐️ 7.0/10

An open-source AWS Trainium2 inference engine for GLM-5.3-Flash was optimized by rewriting layer halves as NKI megakernels. In an early KDA layer at batch 1, the recurrence was only 2% of the attention half, while the mHC pre-projection took 36%, XLA glue 33%, transposes 10%, stream mix 10%, and other small ops 8%. Each kernel keeps the working set in 28 MiB SBUF, splits the weight stream across both physical cores of a logical core, and overlaps in-kernel work with collectives. Together these changes reduced a batch-8 decode step from 32.2 ms in the 17 October build to 24.2 ms by 1 November, with the fused sparse-attention layer and the KDA/MoE kernels each saving 3.2 ms. The remaining time was 6.1 ms memory floor, 10.0 ms engine busy, 4.6 ms in-kernel waits, 2.8 ms exposed collectives, and 0.7 ms idle.

reddit · r/MachineLearning · /u/WildCard727 · Nov 4, 21:47

**「Background」** AWS Trainium2 is a custom AI accelerator whose logical NeuronCores pair physical cores with 28 MiB of on-chip SBUF each; NKI is the low-level kernel language for these devices. GLM-5.3-Flash is a 320B mixture-of-experts model with 1M-token context and KDA linear-attention layers. Decode steps on such hardware are often dominated by fixed-cost kernel launches, HBM write-backs, and cross-chip collectives rather than model arithmetic.

**「Impact」** For developers serving GLM-5.3-Flash on AWS Trainium2, the open-source trnrt engine cuts batch-8 decode latency from 32.2 ms to 24.2 ms and reports up to 28.9 AgentX requests per minute on one trn2.48xlarge. No stock-AWS Neuron or GPU baseline is available for comparison.
